# Halton-MaskGIT — large 384 / cfg=0.5   LazyMAR Token Cache sweep
#
# Model    : ImageNet_384_large.pth (H-MaskGIT-L, 480M, 24 层 / 1024 dim / 24^2+1=577 token)
# Sampler  : halton, step=32, cfg_w=0.5, fp32, seed=42, global_bsize=32, 50000 imgs
#            —— Halton 顺序 / step gate / 温度 / CFG 与 baseline 完全一致, 未改动。
# Gate     : step 5..30, layer 3..21  (与 ffn/attn cache sweep 相同, 保证可比)
#
# 方案 (HALTON_LAZY_CACHE=1), 迁移自 LazyMAR (ICCV'25):
#   选点 : active = U_{t-1} ∪ U_t ∪ register ∪ TopK(入口层 V 相对上一步的余弦变化量)
#          名额 k = ceil((1 - HALTON_LAZY_CACHE_RATIO) * N), 固定名额而非阈值。
#          对应 LazyMAR 的 _prune_tokens (cos(V_l3(t), V_l3(t-1)) + RETAIN_RATIO)。
#   执行 : Q 只算 active token; K/V 走 per-layer 全长缓存 (active 行重算后 scatter
#          回缓存) —— 双向 self-attention 的上下文保持完整; FFN 只算 active token。
#          对应 LazyMAR 的 DecoderAttention masked_scatter_ + DecoderBlock 剪枝。
#   回填 : 区间出口层用缓存回填 inactive 行 (LazyMAR 填 0, 这里不能填 0, 因为
#          Halton 采样器对全部 token 采样并记入 l_codes)。
#
# 与既有方案的唯一概念差别 = "哪些 token 被重算":
#   既有 ffn/attn/layer cache : active = U_{t-1} ∪ U_t, 纯调度决定, 恒为 4~6% token
#   本方案                    : 调度强制集合 + 内容自适应补足到给定预算, 比例可调
#
# 对照 (同 sampler / 同 seed / 同 gate):
#   baseline (无 cache)                 FID 2.5410  IS 256.15
#   ffn   cache  N=2 / norefresh        FID 2.665  / 6.0475
#   attn  cache  N=2 / norefresh        FID 2.7001 / 12.7083
#   layer cache  N=2 / N=4 / norefresh   FID 2.6953 / 3.1822 / 10.7726
#
# 相对耗时实测 (随机权重, batch 4 + CFG, 32 step, 577 token, 24 层, A6000):
#          baseline 1.00x | ffn cache 1.33x | layer cache 1.67x
#   lazy r=0.5 1.34x | r=0.75 1.66x | r=0.9 1.95x | r=0.95 2.03x
#   (lazy 在重算更多 token 的同时更快, 因为 K/V 走显式 per-layer 缓存, 不必每层对
#    全部 token 重算 wk/wv —— 既有 layer cache 每层都要对 577 个 token 重算 K/V。)
#   只反映算力, FID 必须用真实 checkpoint 测。
#
# !! 用随机权重做任何数值验证时注意: Transformer.initialize_weights 会把每个 Block
#    的 AdaLN 调制层零初始化 (DiT 风格), 于是 alpha1=alpha2=0, x = x + alpha*(...)
#    退化成恒等映射, 整个 transformer 什么都不做 —— 那样任何 cache 对比都会平凡
#    通过。test_lazy_token_cache.make_trainer 会重新随机化这些门, T0 负责守卫。
#
# 正确性自检: HALTON_LAZY_CACHE_RATIO=0 时与 baseline 逐位一致 —— 已在真实规模
#   (24 层 / 1024 dim / 577 token / 32 step / CFG, 479M) 上验证全 32 步 logits /
#   codes / image 逐位相同。见 python test_lazy_token_cache.py (11/11) 与
#   python test_cache_regression.py (既有方案 6/6 逐位不变)。
#   跑 sweep 前建议先跑一次 r=0 确认环境无误。
#
# 跑法: LAZY_RATIO=0.9 REFRESH_N=2 bash launch/eval_fid_large384_lazycache.sh
#
# columns: config_name  FID  IS  runtime  notes
# ------------------------------------------------------------

# ============================================================================
# 【结论 1】lazy ≡ layer-output cache, 已由 50k FID 证实
#
#   同 refresh N / 同 24 层, 两者 FID 逐点重合:
#     N     layercache   lazy       Δ
#     2     2.6953       2.6951     0.0002
#     4     3.1822       3.1899     0.0077
#     none 10.7726      10.8181     0.0455
#
#   机理: AdaLN 的 cond 只有类别嵌入 (Network/transformer.py:909-910, 无 step/time
#   embedding), 故 gamma/beta/alpha 在 32 步内恒定。于是 layer cache 每层对全部 577
#   个 token 重算的 K/V, 与 lazy 缓存里那份数在数学上完全相同 —— layer cache 的全长
#   K/V 重算是纯浪费, 不是"用近似换速度"。
#   非逐位相同的原因: (a) lazy 强制 register token active (transformer.py:941),
#   layer cache 不强制; (b) gather/scatter 与 bool-mask 索引的 fp32 非结合性使采样
#   轨迹发散。统计上等价。
#
# 【结论 2】等质量净增益 (同 N 同 FID, batch=16 单卡 A6000 实测)
#
#   config              FID(50k)   transf ms/img   speedup    净增益
#   baseline              2.5410      2007.28      1.000x       —
#   layercache N=2        2.6953      1556.37      1.290x
#   lazy       N=2        2.6951      1292.35      1.553x      1.204x
#   layercache N=4        3.1822      1340.34      1.498x
#   lazy       N=4        3.1899       951.85      2.109x      1.408x
#   layercache N=none    10.7726      1090.27      1.841x
#   lazy       N=none    10.8181       556.26      3.609x      1.960x
#
#   实测净增益 > 理论净增益 (N=2: 1.204x 实测 vs 1.12x 理论), 因为 layer cache 每层
#   每步还要 cached_layer_output.clone() 一份 577x1024 全长张量 + bool-mask 非连续
#   索引, 这些访存开销不计入 FLOPs; lazy 的 (b,k,C) 连续 gather/scatter 轻得多。
#
# 【结论 3】r=1 方案的根本矛盾
#
#   lazy 相对 layer cache 的优势只在 partial 步兑现, 优势随 partial 步占比增长:
#     partial 占比 26/32 (none) -> 净增益 1.960x
#     partial 占比 19/32 (N=4)  -> 净增益 1.408x
#     partial 占比 13/32 (N=2)  -> 净增益 1.204x
#   而 FID 的要求恰好相反 —— 要好 FID 就要多全量步。两个诉求直接冲突。
#   在可用质量点 (FID 2.695) 上, 等质量净增益只有 1.204x。
#
#   下一步唯一还剩的杠杆: rolling refresh (每步额外重算 A 个最陈旧 token,
#   A=576/S, 成本与周期 S 的全刷相当但陈旧度均匀分布), 针对的正是"周期性全刷让
#   576 个 token 同步老化、刷新前一刻全体最劣"这个失效模式。
